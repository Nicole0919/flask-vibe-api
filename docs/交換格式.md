# 個人記帳系統 API 資料交換格式規格書

本文件為前端與個人記帳系統後端（Flask REST API）對接之**資料交換格式規格書**（Exchange Format Specification）。前端開發與資料介接以此份規格為準，無須翻閱後端內部路由原始碼。

---

## 一、 共通通則與規格規範

### 1. 外層固定封裝結構（三個鍵）
所有 API 回應的 JSON 外層結構一律包含三個固定鍵：
- `code`（`integer`）：HTTP 狀態碼（例如 `200`、`201`、`400`、`404`、`500`）。
- `message`（`string`）：給人類閱讀的提示訊息（繁體中文），不含內部資料庫表名、約束代碼或例外堆疊。
- `data`（`object` / `array` / `null`）：實際業務資料本體。單筆資源為 JSON 物件，清單資源為 JSON 陣列；失敗或查無資料時一律為 `null`。

```json
{
  "code": 200,
  "message": "查詢成功",
  "data": {}
}
```

### 2. HTTP 狀態碼對照標準
- `200 OK`：成功查詢（GET）、成功部分更新（PATCH）、成功作廢交易或執行批次開獎對獎。若清單無資料，依然回傳 `200` 且 `data: []`。
- `201 Created`：成功新增資源（POST）。`data` 回傳該列資料庫實際寫入的完整內容（包含資料庫產生的 `id` 與 `created_at`）。
- `400 Bad Request`：請求格式不合法、必填欄位缺漏、數值非正數、業務邏輯不合（如賣出超過庫存）或違反資料庫唯一約束（如名稱重複）。`data` 為 `null`。
- `404 Not Found`：找不到指定的單筆資源（例如特定 ID 不存在）。`data` 為 `null`。
- `500 Internal Server Error`：伺服器內部非預期錯誤或資料庫連線失敗。`data` 為 `null`，原始錯誤細節僅記錄於伺服器日誌。

### 3. 客戶端不送的欄位
客戶端在發送 `POST`（新增）或 `PATCH`（更新）請求時，**嚴禁或不需要傳送下列系統管理欄位**，若客戶端傳送後端亦會直接略過不採用：
- `id`：資料庫代理整數主鍵，由資料庫自動遞增產生。
- `created_at`：資料列建立時間，由資料庫於插入當下自動填入 UTC 時間。
- `updated_at`：資料列更新時間，由後端程式於更新成功時自動刷新 UTC 時間。

### 4. 日期、時間與數值型別定義
- **日期（Date）**：一律使用 ISO 8601 日期字串，格式為 `YYYY-MM-DD`（例如 `"2026-01-15"`）。
- **時間戳記（Timestamp）**：一律使用含 UTC 時區之 ISO 8601 字串（例如 `"2026-11-14T03:19:27.523342+00:00"`）。
- **金額與數值（Amount / Price / Rate / Quantity）**：在 JSON 中一律呈現為數值型別（JSON `number`，浮點數或整數），不加千分號或雙引號字串（例如 `70.0`、`500.0`、`1.0`）。
- **幣別（Currency）**：一律為 3 碼大寫 ISO 4217 英文字母（如 `"TWD"`、`"USD"`）。

### 5. 可空欄位之表現行為
- 資料庫中允許為空（Nullable）之欄位，在回應 JSON 中若無值**一律明確呈現為 `null`**。
- 客戶端在傳送請求時，於選填欄位傳送 JSON `null` 與直接省略該欄位鍵名具備相同效果。

## 二、 查詢參數規格彙整

所有查詢參數皆由後端以 ORM 參數化機制安全繫結，禁止將使用者輸入拼接至 SQL 語句中：

| 資源與端點 | 查詢參數名稱 | 型別與格式 | 說明 |
| :--- | :--- | :--- | :--- |
| `GET /api/incomes` | `account_id`<br>`category_id`<br>`date_from`<br>`date_to` | `integer`<br>`integer`<br>`YYYY-MM-DD`<br>`YYYY-MM-DD` | 篩選指定帳戶<br>篩選指定入帳分類<br>篩選起始入帳日期（含）<br>篩選結束入帳日期（含） |
| `GET /api/expenses` | `account_id`<br>`category_id`<br>`invoice_id`<br>`date_from`<br>`date_to` | `integer`<br>`integer`<br>`integer`<br>`YYYY-MM-DD`<br>`YYYY-MM-DD` | 篩選指定支付帳戶<br>篩選指定花費分類<br>篩選指定關聯發票<br>篩選起始消費日期（含）<br>篩選結束消費日期（含） |
| `GET /api/invoices` | `period_key`<br>`prize_status` | `YYYY-MM`<br>`string` | 篩選開立日落在該雙月期別之發票（如 `2026-01`）<br>篩選兌獎狀態（`unchecked`/`lost`/`won`/`claimed`/`void`） |
| `GET /api/trades` | `instrument_id`<br>`account_id` | `integer`<br>`integer` | 篩選特定投資標的之交易<br>篩選特定交割帳戶之交易 |
| `GET /api/summary` | `month`（**必填**） | `YYYY-MM` | 指定月度生活現金流統計月份（例如 `2026-08`） |

## 三、 各業務資源成功回應範例與欄位表

> **註**：以下範例中的資源識別碼 `id` 皆自數字 `1` 起算作為展示，實際執行時請以 API 回傳之 `id` 為準。

### 1. 帳戶（Accounts）

#### (1) 資源欄位表
| 欄位名稱 | 型別 | 必填/可空 | 說明 |
| :--- | :--- | :--- | :--- |
| `id` | `integer` | 系統產生 | 帳戶唯一識別碼 |
| `name` | `string` | 必填，唯一 | 帳戶名稱（不得重複） |
| `kind` | `string` | 必填 | 帳戶種類：`cash`（現金）、`bank`（銀行）、`credit_card`（信用卡）、`broker`（券商交割戶） |
| `currency` | `string` | 必填，預設 TWD | 計價幣別代碼（3 碼大寫英文字母） |
| `opening_balance` | `number` | 必填，預設 0 | 期初餘額 |
| `statement_day` | `integer` | 可空 | 信用卡結帳日（1~31） |
| `payment_day` | `integer` | 可空 | 信用卡繳款日（1~31） |
| `created_at` | `string` | 系統產生 | 建立時間戳記（UTC ISO 8601） |
| `updated_at` | `string` | 系統產生 | 更新時間戳記（UTC ISO 8601） |

#### (2) 成功回應範例：建立現金錢包帳戶（`POST /api/accounts` $\rightarrow$ `201 Created`）
```json
{
  "code": 201,
  "message": "帳戶建立成功",
  "data": {
    "id": 1,
    "name": "現金錢包",
    "kind": "cash",
    "currency": "TWD",
    "opening_balance": 0.0,
    "statement_day": null,
    "payment_day": null,
    "created_at": "2026-11-14T03:19:27.523342+00:00",
    "updated_at": "2026-11-14T03:19:27.523342+00:00"
  }
}
```

#### (3) 帳戶餘額查詢回應範例（`GET /api/accounts/1/balance` $\rightarrow$ `200 OK`）
```json
{
  "code": 200,
  "message": "查詢餘額成功",
  "data": {
    "account_id": 1,
    "currency": "TWD",
    "balance": 200.0,
    "balance_twd": 200.0
  }
}
```

| `updated_at` | `string` | 系統產生 | 更新時間戳記（UTC ISO 8601） |

### 4. 統一發票與品項明細（Invoices & Invoice Items）

#### (1) 發票主檔欄位表
| 欄位名稱 | 型別 | 必填/可空 | 說明 |
| :--- | :--- | :--- | :--- |
| `id` | `integer` | 系統產生 | 發票唯一識別碼 |
| `number` | `string` | 必填，唯一 | 發票號碼（固定 2 碼大寫英文 + 8 碼數字） |
| `issued_on` | `string` | 必填 | 開立日期（`YYYY-MM-DD`） |
| `amount` | `number` | 必填 | 發票總金額（必須 $>0$） |
| `kind` | `string` | 必填 | 發票種類：`paper`（紙本）或 `electronic`（電子） |
| `currency` | `string` | 必填，預設 TWD | 計價幣別（3 碼大寫英文字母） |
| `fx_rate_to_twd` | `number` | 必填，預設 1.0 | 對新台幣匯率 |
| `random_code` | `string` | 可空 | 4 碼防偽隨機碼 |
| `seller_name` | `string` | 可空 | 賣方商家名稱 |
| `seller_ban` | `string` | 可空 | 賣方統一編號（8 碼數字） |
| `prize_status` | `string` | 必填，預設 unchecked | 兌獎狀態：`unchecked`、`lost`、`won`、`claimed`、`void` |
| `items` | `array` | 單筆額外附加 | 該張發票所屬之商品品項清單 |
| `expense_ids` | `array` | 單筆額外附加 | 關聯掛於此發票的花費明細 ID 清單 |
| `created_at` | `string` | 系統產生 | 建立時間戳記（UTC ISO 8601） |
| `updated_at` | `string` | 系統產生 | 更新時間戳記（UTC ISO 8601） |

| :--- | :--- | :--- |
| `month` | `string` | 查詢統計月份（`YYYY-MM`） |
| `income_twd` | `number` | 該月份所有生活入帳折合新台幣總額（無紀錄時為 `0.0`） |
| `expense_twd` | `number` | 該月份所有生活開銷折合新台幣總額（無紀錄時為 `0.0`） |

#### (2) 成功回應範例：2026-08 月合計（`GET /api/summary?month=2026-08` $\rightarrow$ `200 OK`）
```json
{
  "code": 200,
  "message": "查詢月度收支摘要成功",
  "data": {
    "month": "2026-08",
    "income_twd": 500.0,
    "expense_twd": 70.0
  }
}
```

## 四、 錯誤回應範例（400 與 404）

所有錯誤回應皆保證 `data` 鍵固定為 `null`，且絕不在外層透露任何資料庫表名、SQLSTATE 或約束名稱。

### 1. 400 Bad Request（格式不符或業務限制衝突）
```json
{
  "code": 400,
  "message": "資料格式不正確或違反約束條件",
  "data": null
}
```

### 2. 404 Not Found（查無此列）
```json
{
  "code": 404,
  "message": "找不到這一筆",
  "data": null
}
```

## 五、 內部錯誤（Internal Server Errors & Logging）

> **重要安全性與架構宣告**：
> 本節定義之欄位（如 `error_code`、`error_detail`、`stack_trace`）**純粹記錄於後端伺服器日誌（Server Log）**，供開發與運維排查診斷使用；**絕對不會、也嚴禁暴露在對前端公開的回應 JSON** 中。

### 1. 伺服器日誌物件鍵名規範
| 鍵名 | 型別 | 說明 |
| :--- | :--- | :--- |
| `timestamp` | `string` | 錯誤發生時間（UTC ISO 8601） |
| `request_id` | `string` | 該次 HTTP 請求的唯一追蹤 UUID |
| `path` | `string` | 觸發錯誤的 API 請求路徑 |
| `method` | `string` | 該次請求之 HTTP 方法 |
| `error_code` | `string` | 內部標準化錯誤分類代碼（見下表） |
| `error_detail` | `string` | 資料庫或底層程式拋出之真實錯誤訊息（含 SQLSTATE、Constraint Name） |
| `stack_trace` | `string` | 完整的例外調用堆疊內容 |

### 2. 內部 `error_code` 分類代碼對照表
| 內部錯誤代碼（`error_code`） | 說明 | 對應外部 HTTP 狀態碼 |
| :--- | :--- | :--- |
| `conflict.unique_name` | 唯一名稱重複衝突（如帳戶、入帳分類、花費分類名稱） | `400` |
| `conflict.unique_number` | 統一發票號碼重複衝突 | `400` |
| `conflict.unique_period_tier` | 開獎期別獎項重複設定 | `400` |
| `conflict.unique_market_symbol` | 同一交易市場下投資標的代號重複 | `400` |
| `conflict.unique_invoice_income` | 發票已重複請領中獎入帳 | `400` |
| `conflict.unique_trade_income` | 投資交易已重複請領股利或減資退款入帳 | `400` |
| `validation.invalid_amount` | 金額、單價或小計非正數（$\le 0$） | `400` |
| `validation.invalid_fx_rate` | 對新台幣匯率非正數（$\le 0$） | `400` |
| `validation.invalid_format` | 發票號碼正則格式、幣別代碼或日期字串格式不符 | `400` |
| `validation.empty_fields` | 「來源與備註」或「商家與備註」兩欄位同時為空 | `400` |
| `validation.insufficient_shares` | 賣出或減資股數超過目前有效累積持有股數 | `400` |
| `foreign_key.not_found` | 參照之父列不存在（如分類、帳戶或發票 ID 不存在） | `400` |
| `foreign_key.restrict` | 欲作廢或異動之父列仍被子列參照保護 | `400` |
| `not_found.record` | 查無指定的資源 ID | `404` |
| `database.connection_error` | 資料庫連線逾時、斷線或連線池耗盡 | `500` |

## 六、 與現況的差異

本節逐條整理現行後端實作程式碼與步驟 14 約定之細微差異，以供前端對接時參照（依規範後端程式保持不變）：

| 端點與情境 | 目前後端程式現況 | 步驟 14 之約定與建議相容處理 |
| :--- | :--- | :--- |
| **全域 404 訊息**<br>（所有單筆端點） | 若查無該 ID，目前部分端點回傳個別資源的人話（例如：「找不到此帳戶」、「找不到此入帳分類」、「找不到此花費紀錄」），僅未匹配路由回傳「找不到這一筆」。 | 步驟 14 固定句子為「`找不到這一筆`」。前端判斷邏輯建議以 `code === 404` 或 `data === null` 為準，不要依賴 `message` 的精確字串比對。 |
| **全域 400 錯誤提示**<br>（所有驗證錯誤） | 目前後端回傳具體欄位錯誤訊息（如「帳戶名稱已存在，請使用其他名稱」、「轉出帳戶與轉入帳戶不可相同」）。 | 步驟 14 約定外部統一呈現標準人話「`資料格式不正確或違反約束條件`」，而將具體原因記錄於日誌 `error_code`。前端呈現時可直接顯示後端回傳之 `message` 給使用者。 |
| **月度收支摘要**<br>`GET /api/summary` | 現行後端回傳物件除了 `month`、`income_twd`、`expense_twd` 之外，額外計算並回傳了淨現金流 `net_twd`（$\text{income} - \text{expense}$）。 | 步驟 14 核心約定為包含 `month`、`income_twd`、`expense_twd`。前端若僅取用此三項欄位可完全相容，若需淨現金流亦可直接使用後端額外提供的 `net_twd`。 |
| **發票對獎回傳鍵名**<br>`POST /api/draw-periods/<id>/check` | 現行後端回傳 `{"checked_count": X, "won_count": Y}`。 | 完全符合步驟 14「回傳對過的張數與中獎張數」之約定。 |
