# 個人記帳系統資料表設計說明書

本文件為個人記帳系統（Supabase PostgreSQL）之關聯式資料庫結構設計規格書。本設計專為個人單機／自用帳本打造，不涉及多使用者帳號與複雜權限，聚焦於四本核心冊子：**入帳**、**花費**、**投資**、**發票**，以及跨帳戶的**資產移轉**。

---

## 一、 全域設計通則與規範

1. **命名規範**：
   - 資料表與欄位名稱一律使用小寫英文字母，單字之間以半形底線（`snake_case`）分隔。
   - 所有外鍵欄位名稱一律以被參照表之單數名稱加上 `_id` 命名（例如：`account_id`、`invoice_id`）。
2. **主鍵設計**：
   - 每張表皆採用資料庫自動產生、建立後不可更改的整數主鍵（PostgreSQL 之 `BIGINT GENERATED ALWAYS AS IDENTITY` 或 `BIGSERIAL`），型別為 `bigint`。
3. **時間戳記**：
   - 每一張表皆包含 `created_at` 與 `updated_at` 兩個欄位。
   - 時間欄位型別一律採用含時區的 `timestamptz`。
   - `created_at`：於資料列插入時由資料庫自動填入當前 UTC 時間（`DEFAULT timezone('utc', now())`），寫入後不可異動。
   - `updated_at`：於資料列更新時由後端 API 程式明確填入當前 UTC 時間。
4. **金額與幣別**：
   - 所有金額與單價欄位一律採用可含小數之定點數型別 `numeric(16, 4)`，避免浮點運算誤差。
   - 所有幣別欄位一律採用三碼大寫 ISO 4217 字母代碼（型別 `char(3)`，例如 `'TWD'`、`'USD'`、`'JPY'`）。
   - 每一筆涉及金額的交易皆保留相對於新台幣的匯率 `exchange_rate_to_twd`（型別 `numeric(12, 6)`），若交易幣別為新台幣（TWD），匯率固定為 `1.000000`。
5. **外鍵約束與刪除行為**：
   - 嚴格遵守「父列仍被其他子列參照時不可刪除」（PostgreSQL 預設的 `ON DELETE RESTRICT`）。
   - 全系統唯一的例外為「**統一發票品項明細**（`invoice_items`）」，當發票主檔被刪除時，其品項隨同主檔一起消失（`ON DELETE CASCADE`）。
6. **不實體儲存衍生狀態**：
   - 各帳戶的「目前餘額」與各投資標的的「目前持有股數、平均成本」皆不開闢可變更的欄位儲存，全面透過歷史明細列即時動態計算，避免資料不一致與競態條件。
7. **規則實作分界**：
   - 資料庫層級：以 `NOT NULL`、`CHECK`、`UNIQUE`、`FOREIGN KEY` 與 `EXCLUDE` 明確約束。
   - 複雜商務邏輯與順序校驗：標註為「由 API 在寫入前檢查」。

## 二、 資料表詳細設計

系統包含以下 12 張核心資料表：

1. `accounts`（帳戶表）
2. `transfers`（帳戶移轉明細表）
3. `income_categories`（入帳分類表）
4. `expense_categories`（花費分類表）
5. `incomes`（入帳明細表）
6. `expenses`（花費明細表）
7. `invoices`（統一發票主表）
8. `invoice_items`（統一發票品項明細表）
9. `invoice_prize_tiers`（統一發票獎別與獎金設定表）
10. `invoice_lottery_results`（統一發票各期中獎號碼表）
11. `investment_targets`（投資標的主表）
12. `investment_transactions`（投資交易明細表）

---

### 1. 帳戶表（`accounts`）

- **在記什麼**：記錄個人所有持有的實體或虛擬金融容器（現金皮夾、各家銀行活儲帳戶、信用卡、券商交割戶）。
- **為什麼單獨成表**：資金必須具體落地於特定媒介上。入帳是資金流入容器、花費是資金流出容器、移轉是容器間位移，且不同容器有獨立的幣別與性質，必須獨立管理。

| 欄位名稱 | 型別 | 必填/可空 | 鍵與限制 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | PRIMARY KEY (自動產生) | 帳戶唯一識別碼 |
| `name` | `varchar(100)` | 必填 | UNIQUE | 帳戶名稱（如：台新 Richart、中信英雄聯盟卡、台幣現金皮夾），不得重複 |
| `account_type` | `varchar(20)` | 必填 | CHECK | 帳戶型態，僅允許：`cash`（現金）、`bank`（銀行）、`credit_card`（信用卡）、`brokerage`（券商交割戶） |
| `currency` | `char(3)` | 必填 | CHECK (3碼大寫) | 帳戶計價主幣別，預設 `'TWD'` |
| `description` | `text` | 可空 | 無 | 備註說明 |
| `created_at` | `timestamptz` | 必填 | DEFAULT timezone('utc', now()) | 建立時間（UTC） |
| `updated_at` | `timestamptz` | 必填 | 無 | 由 API 更新時間（UTC） |

- **約束與校驗**：
  - `name` 具唯一性約束（`UNIQUE`）。
  - `account_type IN ('cash', 'bank', 'credit_card', 'brokerage')` 由 PostgreSQL `CHECK` 約束強制保證。
  - `currency ~ '^[A-Z]{3}$'` 由 PostgreSQL `CHECK` 約束保證。

---

### 2. 帳戶移轉明細表（`transfers`）

- **在記什麼**：記錄資金從一個內部帳戶流動到另一個內部帳戶的歷程（例如：銀行提款至現金皮夾、銀行轉帳至券商交割戶、銀行扣繳信用卡款）。
- **為什麼單獨成表**：移轉本質上「既非入帳（總資產未增加），亦非花費（總資產未減少）」，僅是資產配置位移。若將其拆成一正一負的入帳與花費，會嚴重扭曲損益與收支報表，因此必須作為獨立事件記錄。

| 欄位名稱 | 型別 | 必填/可空 | 鍵與限制 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | PRIMARY KEY (自動產生) | 移轉唯一識別碼 |
| `from_account_id` | `bigint` | 必填 | FOREIGN KEY (`accounts.id`) | 來源（扣款）帳戶，ON DELETE RESTRICT |
| `to_account_id` | `bigint` | 必填 | FOREIGN KEY (`accounts.id`) | 目的（入款）帳戶，ON DELETE RESTRICT |
| `transacted_at` | `timestamptz` | 必填 | 無 | 移轉發生時間 |
| `out_amount` | `numeric(16, 4)` | 必填 | CHECK (> 0) | 來源帳戶扣除金額 |
| `out_currency` | `char(3)` | 必填 | CHECK (3碼大寫) | 來源帳戶幣別 |
| `in_amount` | `numeric(16, 4)` | 必填 | CHECK (> 0) | 目的帳戶收到金額（支援不同幣別換匯移轉） |
| `in_currency` | `char(3)` | 必填 | CHECK (3碼大寫) | 目的帳戶幣別 |
| `fee` | `numeric(16, 4)` | 必填 | DEFAULT 0, CHECK (>= 0) | 跨行轉帳手續費（自來源帳戶額外扣除） |
| `exchange_rate_to_twd` | `numeric(12, 6)` | 必填 | DEFAULT 1.0, CHECK (> 0) | 該筆轉帳基準對新台幣匯率 |
| `note` | `text` | 可空 | 無 | 移轉備註說明 |
| `created_at` | `timestamptz` | 必填 | DEFAULT timezone('utc', now()) | 建立時間（UTC） |
| `updated_at` | `timestamptz` | 必填 | 無 | 由 API 更新時間（UTC） |

- **約束與校驗**：
  - 來源與目的帳戶不能相同：`CHECK (from_account_id <> to_account_id)`。
  - 金額與匯率正數防呆：`CHECK (out_amount > 0 AND in_amount > 0 AND fee >= 0 AND exchange_rate_to_twd > 0)`。
  - 來源與目的幣別若相同，API 在寫入前檢查 `out_amount == in_amount`；若涉及換匯則由 API 驗證合理性。

### 3. 入帳分類表（`income_categories`）

- **在記什麼**：記錄收入的歸類名目（例如：薪資、年終獎金、銀行利息、發票中獎、股票現金股利、退款）。
- **為什麼單獨成表**：將分類獨立規範化成表，可防止輸入錯字導致報表統計破碎，並維持名稱唯一性。

| 欄位名稱 | 型別 | 必填/可空 | 鍵與限制 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | PRIMARY KEY (自動產生) | 入帳分類唯一識別碼 |
| `name` | `varchar(50)` | 必填 | UNIQUE | 分類名稱（如：薪資、利息、投資收益），不可重複 |
| `description` | `text` | 可空 | 無 | 分類用途備註 |
| `created_at` | `timestamptz` | 必填 | DEFAULT timezone('utc', now()) | 建立時間（UTC） |
| `updated_at` | `timestamptz` | 必填 | 無 | 由 API 更新時間（UTC） |

- **約束與校驗**：
  - `name` 具唯一性約束（`UNIQUE`）。

---

### 4. 花費分類表（`expense_categories`）

- **在記什麼**：記錄支出的歸類名目（例如：餐飲、生活用品、交通、娛樂、水電瓦斯、醫療）。
- **為什麼單獨成表**：與入帳分類徹底分離，滿足約束條件「入帳與花費的分類分開，名稱各自不能重複」，方便日後各自擴充或停用。

| 欄位名稱 | 型別 | 必填/可空 | 鍵與限制 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | PRIMARY KEY (自動產生) | 花費分類唯一識別碼 |
| `name` | `varchar(50)` | 必填 | UNIQUE | 分類名稱（如：外食飲食、水電瓦斯、租金），不可重複 |
| `description` | `text` | 可空 | 無 | 分類用途備註 |
| `created_at` | `timestamptz` | 必填 | DEFAULT timezone('utc', now()) | 建立時間（UTC） |
| `updated_at` | `timestamptz` | 必填 | 無 | 由 API 更新時間（UTC） |

- **約束與校驗**：
  - `name` 具唯一性約束（`UNIQUE`）。

---

### 5. 入帳明細表（`incomes`）

- **在記什麼**：所有實體資金流入事件。包含日常薪資、一般進款，以及兩大特殊來源：**統一發票中獎獎金**與**投資產生的現金收入（現金股利、減資退回現金）**。
- **為什麼單獨成表**：作為四大核心冊子之一，集中管理所有增加總資產的入款流水帳。

| 欄位名稱 | 型別 | 必填/可空 | 鍵與限制 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | PRIMARY KEY (自動產生) | 入帳流水唯一識別碼 |
| `account_id` | `bigint` | 必填 | FOREIGN KEY (`accounts.id`) | 資金存入之帳戶，ON DELETE RESTRICT |
| `category_id` | `bigint` | 必填 | FOREIGN KEY (`income_categories.id`) | 入帳分類，ON DELETE RESTRICT |
| `amount` | `numeric(16, 4)` | 必填 | CHECK (> 0) | 入帳實收金額 |
| `currency` | `char(3)` | 必填 | CHECK (3碼大寫) | 入帳幣別 |
| `exchange_rate_to_twd` | `numeric(12, 6)` | 必填 | DEFAULT 1.0, CHECK (> 0) | 換算新台幣匯率（台幣填 1.0） |
| `received_at` | `timestamptz` | 必填 | 無 | 資金入帳時間 |
| `invoice_id` | `bigint` | 可空 | FOREIGN KEY (`invoices.id`), UNIQUE | 若此筆為發票中獎獎金，指向對應發票；一張發票最多一筆入帳 |
| `investment_transaction_id` | `bigint` | 可空 | FOREIGN KEY (`investment_transactions.id`), UNIQUE | 若此筆為現金股利或減資退款，指向對應投資交易；一筆交易最多一筆入帳 |
| `note` | `text` | 可空 | 無 | 備註說明 |
| `created_at` | `timestamptz` | 必填 | DEFAULT timezone('utc', now()) | 建立時間（UTC） |
| `updated_at` | `timestamptz` | 必填 | 無 | 由 API 更新時間（UTC） |

- **約束與校驗**：
  - 金額與匯率檢核：`CHECK (amount > 0 AND exchange_rate_to_twd > 0)`。
  - 發票中獎一對一限制：`invoice_id` 設有唯一約束（`UNIQUE`），保證同一張發票至多只能有一筆中獎入帳。
  - 投資現金返還一對一限制：`investment_transaction_id` 設有唯一約束（`UNIQUE`），保證同一筆投資交易（現金股利或減資）至多只能產生一筆入帳。
  - 外鍵刪除約束：所有外鍵皆為 `ON DELETE RESTRICT`。
  - 由 API 在寫入前檢查：若關聯 `investment_transaction_id`，該投資交易之型態必須為 `cash_dividend` 或 `capital_reduction`。

### 6. 花費明細表（`expenses`）

- **在記什麼**：所有資金流出事件。記錄日常生活各項開銷，支援信用卡「消費日」與「扣款日」跨日期的特性，並可關聯到實體發票。
- **為什麼單獨成表**：作為四大核心冊子之一，集中管理所有減少總資產的開銷流水帳。

| 欄位名稱 | 型別 | 必填/可空 | 鍵與限制 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | PRIMARY KEY (自動產生) | 花費流水唯一識別碼 |
| `account_id` | `bigint` | 必填 | FOREIGN KEY (`accounts.id`) | 支付帳戶（若為信用卡，此處填信用卡帳戶），ON DELETE RESTRICT |
| `category_id` | `bigint` | 必填 | FOREIGN KEY (`expense_categories.id`) | 花費分類，ON DELETE RESTRICT |
| `invoice_id` | `bigint` | 可空 | FOREIGN KEY (`invoices.id`) | 關聯之統一發票 ID，可多筆花費對應同一張發票，ON DELETE RESTRICT |
| `amount` | `numeric(16, 4)` | 必填 | CHECK (> 0) | 花費金額 |
| `currency` | `char(3)` | 必填 | CHECK (3碼大寫) | 交易幣別 |
| `exchange_rate_to_twd` | `numeric(12, 6)` | 必填 | DEFAULT 1.0, CHECK (> 0) | 換算新台幣匯率（台幣填 1.0） |
| `spent_at` | `timestamptz` | 必填 | 無 | 實際消費發生日與時間 |
| `settlement_date` | `date` | 可空 | 無 | 實際扣款日／結算日（例如信用卡次月扣款日，現金消費通常與消費日同天或為空） |
| `note` | `text` | 可空 | 無 | 花費備註說明 |
| `created_at` | `timestamptz` | 必填 | DEFAULT timezone('utc', now()) | 建立時間（UTC） |
| `updated_at` | `timestamptz` | 必填 | 無 | 由 API 更新時間（UTC） |

- **約束與校驗**：
  - 金額與匯率檢核：`CHECK (amount > 0 AND exchange_rate_to_twd > 0)`。
  - 外鍵刪除約束：所有外鍵包含 `invoice_id` 皆為 `ON DELETE RESTRICT`（當花費還指著這張發票時，該發票不得被刪除）。
  - 多對一關聯：`invoice_id` **不加 UNIQUE 約束**，允許一張發票對應多筆花費（例如同一張賣場發票，拆帳分屬「食品」與「文具」兩筆不同分類的花費），且各筆花費合計不必等於發票總額。

### 7. 統一發票主表（`invoices`）

- **在記什麼**：台灣統一發票主檔資訊，記錄字軌號碼、開立日期、發票金額、開獎期別與賣方統編。
- **為什麼單獨成表**：發票本身有完整的生命週期（開立、留底、品項清單、開獎對獎、獎金入帳、費用報銷勾稽），具有獨立於單一花費的實體價值。

| 欄位名稱 | 型別 | 必填/可空 | 鍵與限制 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | PRIMARY KEY (自動產生) | 發票唯一識別碼 |
| `invoice_number` | `char(10)` | 必填 | CHECK (格式規範) | 統一發票號碼，固定 2 碼大寫英文字母 + 8 碼數字（如：`AB12345678`） |
| `period` | `char(7)` | 必填 | CHECK (格式規範) | 發票期別，固定 7 碼格式 `YYYY-MM`（如：`2026-01` 代表 2026年 01-02月期） |
| `issued_at` | `date` | 必填 | 無 | 發票開立日期 |
| `total_amount` | `numeric(16, 4)` | 必填 | CHECK (>= 0) | 發票總金額 |
| `seller_tax_id` | `char(8)` | 可空 | CHECK (8碼數字) | 賣方統一編號（8 碼數字） |
| `seller_name` | `varchar(100)` | 可空 | 無 | 賣方商家名稱（如：全家便利商店、家樂福） |
| `note` | `text` | 可空 | 無 | 留底備註 |
| `created_at` | `timestamptz` | 必填 | DEFAULT timezone('utc', now()) | 建立時間（UTC） |
| `updated_at` | `timestamptz` | 必填 | 無 | 由 API 更新時間（UTC） |

- **約束與校驗**：
  - 字軌號碼格式：`CHECK (invoice_number ~ '^[A-Z]{2}[0-9]{8}$')`。
  - 期別格式：`CHECK (period ~ '^[0-9]{4}-(01|03|05|07|09|11)$')`（以每雙月起始月份命名，詳見第六節說明）。
  - 期別與發票號碼聯合唯一：`UNIQUE (period, invoice_number)`，因每期字軌號碼皆會重新指派，同期不可重複。
  - 統編格式檢核：`CHECK (seller_tax_id IS NULL OR seller_tax_id ~ '^[0-9]{8}$')`。
  - 由 API 在寫入前檢查：由 `issued_at` 精確計算並推導 `period`，確認兩者吻合後方可寫入。

### 8. 統一發票品項明細表（`invoice_items`）

- **在記什麼**：單張統一發票上的每一筆明細商品（品名、數量、單價、小計金額）。
- **為什麼單獨成表**：一張發票內含多項商品，屬於典型一對多（1:N）從屬結構。

| 欄位名稱 | 型別 | 必填/可空 | 鍵與限制 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | PRIMARY KEY (自動產生) | 品項唯一識別碼 |

## 三、 餘額與持有股數計算邏輯（不存實體欄位）

為維護資料之單一真實來源（Single Source of Truth），帳戶餘額與投資持有狀態不使用可變欄位儲存，其計算規格如下：

### 1. 帳戶餘額（`account_balance`）計算公式

針對任一帳戶 `A`，截至時間點 $T$ 為止的餘額，由以下明細列彙整求和得出：

$$\text{餘額}_A = \sum \text{入帳} - \sum \text{花費} + \sum \text{移入} - \sum \text{移出} - \sum \text{移出手續費} - \sum \text{投資買進流出} + \sum \text{投資賣出流入}$$

各項目具體對應之資料列：
1. **加項（入帳流入）**：
   `incomes` 表中 `account_id = A` 且 `received_at <= T` 之 `amount` 總和。
2. **減項（花費流出）**：
   `expenses` 表中 `account_id = A` 且 `spent_at <= T` 之 `amount` 總和。（若是信用卡帳戶，此處呈現累積待繳消費；若採結算扣款，可依 `settlement_date` 動態篩選已入帳流水）。
3. **加項（移轉轉入）**：
   `transfers` 表中 `to_account_id = A` 且 `transacted_at <= T` 之 `in_amount` 總和。
4. **減項（移轉轉出）**：
   `transfers` 表中 `from_account_id = A` 且 `transacted_at <= T` 之 `(out_amount + fee)` 總和。
5. **減項（投資買進交割扣款）**：
   `investment_transactions` 表中 `settlement_account_id = A` 且 `transaction_type = 'buy'` 且 `transacted_at <= T` 之 `(total_cash_amount + fee)` 總和。
6. **加項（投資賣出交割入帳）**：
   `investment_transactions` 表中 `settlement_account_id = A` 且 `transaction_type = 'sell'` 且 `transacted_at <= T` 之 `(total_cash_amount - fee - tax)` 總和。
7. **備註（現金股利與減資現金）**：
   若透過 `incomes` 登記並關聯到 `investment_transaction_id`，則已包含在第 1 項「入帳流入」，交割戶直接計算該筆入帳即可，不重複計算。

---

### 2. 投資持有股數（`shares_held`）與平均成本（`average_cost`）計算公式

針對任一投資標的 `S`，截至時間點 $T$ 為止，依據 `investment_transactions` 之時間升冪排序，依**加權平均成本法（Weighted Average Cost Method）**計算：

#### (1) 總持有股數（`shares_held`）
初始化 $\text{股數} = 0$。依序歷遍交易：
- **`buy`（買進）**：$\text{股數} = \text{股數} + \text{shares}$
- **`sell`（賣出）**：$\text{股數} = \text{股數} - \text{shares}$（**由 API 在寫入前檢查：$\text{股數} - \text{shares} \ge 0$**）
- **`stock_dividend`（配股）**：$\text{股數} = \text{股數} + \text{shares}$
- **`dividend_reinvestment`（股息再投入）**：$\text{股數} = \text{股數} + \text{shares}$
- **`stock_split`（分割）**：$\text{股數} = \text{股數} \times \text{split\_ratio}$
- **`stock_consolidation`（合併）**：$\text{股數} = \text{股數} \times \text{split\_ratio}$
- **`capital_reduction`（減資）**：$\text{股數} = \text{股數} - \text{shares}$
- **`cash_dividend`（現金股利）**：股數不變。

#### (2) 平均成本（每股平均成本與總成本庫存）
初始化 $\text{總成本} = 0$，$\text{每股平均成本} = 0$。
- **`buy`**：
  $\text{總成本} = \text{總成本} + (\text{total\_cash\_amount} + \text{fee})$
  $\text{每股平均成本} = \frac{\text{總成本}}{\text{最新股數}}$
- **`dividend_reinvestment`**：
  $\text{總成本} = \text{總成本} + \text{total\_cash\_amount}$
  $\text{每股平均成本} = \frac{\text{總成本}}{\text{最新股數}}$
- **`stock_dividend`**：
  總成本不變，因新發股票稀釋成本：
  $\text{每股平均成本} = \frac{\text{總成本}}{\text{最新股數}}$
- **`stock_split` / `stock_consolidation`**：
  總成本不變，新每股成本依比例放大或縮小：
  $\text{每股平均成本} = \frac{\text{舊每股平均成本}}{\text{split\_ratio}}$
- **`capital_reduction`（退還現金減資）**：
  若有退回現金，扣抵總成本：
  $\text{總成本} = \max(0, \text{總成本} - \text{total\_cash\_amount})$
  $\text{每股平均成本} = \frac{\text{總成本}}{\text{最新股數}}$
- **`sell`**：
  每股平均成本維持不變，僅等比例減少持股總成本：
  $\text{已實現損益} = (\text{total\_cash\_amount} - \text{fee} - \text{tax}) - (\text{shares} \times \text{每股平均成本})$
  $\text{總成本} = \text{總成本} - (\text{shares} \times \text{每股平均成本})$

## 四、 統一發票期別與開獎兌獎機制

### 1. 統一發票期別（`period`）如何由開立日（`issued_at`）決定

台灣統一發票每兩個月為一期，開立日期決定其法定所屬期別。其換算規則如下：

- **換算邏輯**：
  1. 取得開立日期之公曆年份（`YYYY`）與月份（`MM`）。
  2. 若月份為雙數月份（如 2, 4, 6, 8, 10, 12），期別起始月份為 `MM - 1`；若為單數月份，期別起始月份即為 `MM`。
  3. 產出 7 碼統一格式 `YYYY-MM`，其中 `MM` 必為 `01`、`03`、`05`、`07`、`09`、`11` 之一。
- **對應範例**：
  - 開立日為 `2026-01-15` $\rightarrow$ 屬於 **`2026-01`** 期（即 115 年 01-02 月期）
  - 開立日為 `2026-02-28` $\rightarrow$ 屬於 **`2026-01`** 期（即 115 年 01-02 月期）
  - 開立日為 `2026-07-03` $\rightarrow$ 屬於 **`2026-07`** 期（即 115 年 07-08 月期）
  - 開立日為 `2026-12-31` $\rightarrow$ 屬於 **`2026-11`** 期（即 115 年 11-12 月期）
- **約束**：資料表欄位 `period` 加上格式限制 `CHECK (period ~ '^[0-9]{4}-(01|03|05|07|09|11)$')`，並**由 API 在寫入前檢查**，確保傳入的 `period` 與 `issued_at` 換算結果嚴格相符。

### 2. 開獎獎金資料表儲存與自動對獎設計

1. 獎金資料由資料表 `invoice_prize_tiers` 維護，例如：
   - 特別獎：`tier_code = 'special_10m'`, `prize_amount = 10000000.0000`, `match_rule = 'full_8'`
   - 特獎：`tier_code = 'grand_2m'`, `prize_amount = 2000000.0000`, `match_rule = 'full_8'`
   - 頭獎：`tier_code = 'first'`, `prize_amount = 200000.0000`, `match_rule = 'full_8'`
   - 二獎：`tier_code = 'second'`, `prize_amount = 40000.0000`, `match_rule = 'last_7'`
   - 三獎：`tier_code = 'third'`, `prize_amount = 10000.0000`, `match_rule = 'last_6'`
   - 四獎：`tier_code = 'fourth'`, `prize_amount = 4000.0000`, `match_rule = 'last_5'`
   - 五獎：`tier_code = 'fifth'`, `prize_amount = 1000.0000`, `match_rule = 'last_4'`
   - 六獎：`tier_code = 'sixth'`, `prize_amount = 200.0000`, `match_rule = 'last_3'`
2. 各期官方開出號碼填入 `invoice_lottery_results`。
3. 對獎程式由 API 依字尾擷取（`SUBSTRING`）進行比對，命中最高獎項時：
   - 建立一筆 `incomes` 資料列。
   - 將該筆入帳之 `invoice_id` 指向中獎發票之 `invoices.id`。
   - `incomes.invoice_id` 之 `UNIQUE` 約束保證該張發票絕不會被重覆重複請領獎金。

## 五、 投資交易種類與限制設計

系統之 `investment_transactions.transaction_type` 支援 8 種法定與市場交易行為：

| 交易種類（`transaction_type`） | 說明 | 股數（`shares`） | 單價（`price_per_share`） | 現金總額（`total_cash_amount`） | 是否可產生入帳（`incomes`） |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `buy` | 現金買進股票 | 必填（$>0$） | 必填（$>0$） | 必填（$>0$） | 否（由交割戶扣款） |
| `sell` | 賣出持股換回現金 | 必填（$>0$） | 必填（$>0$） | 必填（$>0$） | 否（由交割戶收款） |
| `cash_dividend` | 發放現金股利 | 填 $0$ | 可為空 | 必填（$>0$） | **是**（可產生 1 筆關聯入帳） |
| `stock_dividend` | 無償配發股票股利 | 必填（$>0$） | 可為空 | 填 $0$ | 否 |
| `dividend_reinvestment` | 股息自動再投資買股 | 必填（$>0$） | 必填（$>0$） | 必填（$>0$） | 否 |
| `stock_split` | 股票分割（如 1 股拆 2 股） | 必填（變動後股數差額） | 可為空 | 填 $0$ | 否 |
| `stock_consolidation` | 股票合併（反向分割） | 必填（減少股數） | 可為空 | 填 $0$ | 否 |
| `capital_reduction` | 減資（包含退還現金減資） | 必填（註銷減少股數） | 可為空 | 可填退還現金總額（$\ge 0$） | **是**（若有退還現金，可產生 1 筆關聯入帳） |

- **防呆規則（賣出不得使持有小於 0）**：
  - **由 API 在寫入前檢查**：當使用者發起 `sell`、`stock_consolidation`、`capital_reduction` 時，後端 API 必須先行計算當前累積可用股數 $\text{AvailableShares}$。若欲扣減之股數小於 $\text{AvailableShares}$，則拒絕該筆寫入並回報錯誤訊息。

## 六、 關聯與限制條件彙整一覽

| 業務限制規則 | 實作機制 | 具體定義方式 |
| :--- | :--- | :--- |
| 入帳分類名稱唯一 | PostgreSQL 約束 | `income_categories.name UNIQUE` |
| 花費分類名稱唯一 | PostgreSQL 約束 | `expense_categories.name UNIQUE` |
| 移轉來源帳戶與目的帳戶不可相同 | PostgreSQL 約束 | `transfers.CHECK (from_account_id <> to_account_id)` |
| 統一發票號碼為 2 碼大寫英文字母 + 8 碼數字 | PostgreSQL 約束 | `invoices.CHECK (invoice_number ~ '^[A-Z]{2}[0-9]{8}$')` |
| 統一發票每期每號碼唯一 | PostgreSQL 約束 | `invoices.UNIQUE (period, invoice_number)` |
| 發票品項隨發票刪除一同消失 | PostgreSQL 外鍵 | `invoice_items.invoice_id REFERENCES invoices(id) ON DELETE CASCADE` |
| 任何已參照之父列不得任意刪除 | PostgreSQL 外鍵 | 其餘所有外鍵全面採用 `ON DELETE RESTRICT` |
| 一張發票最多只能領取一次中獎入帳 | PostgreSQL 約束 | `incomes.invoice_id UNIQUE` |
| 一筆投資交易最多只能產生一次現金入帳 | PostgreSQL 約束 | `incomes.investment_transaction_id UNIQUE` |
| 一張發票可對應多筆花費 | 關聯設計 | `expenses.invoice_id` 為外鍵且不設唯一約束 |
| 花費金額不必等於發票金額 | 業務邏輯允許 | 資料庫層面不強制 `expenses.amount` 總和約束 |
| 投資賣出不得使庫存小於 0 | 業務檢核 | **由 API 在寫入前檢查** |
| 發票開立日與期別之雙月換算一致性 | 業務檢核 | **由 API 在寫入前檢查**（資料庫以正規表達式輔助約束） |
| 現金股利/減資關聯入帳之交易型別查核 | 業務檢核 | **由 API 在寫入前檢查**（限關聯至指定型態之投資交易） |

## 七、 這一次不建的表

依據專案階段性範圍與指示，本階段專注於穩固個人基本記帳本體結構，以下項目**這一次明確不建表**，並列出日後若有需求時的擴充考量：

1. **預算表（`budgets`）**：
   - *不建理由*：本次核心為記錄事實發生的交易流水與真實資產。預算屬於事前規劃與分析目標，不影響帳戶資金餘額之計算，延後至報表與分析模組階段再行擴充。
2. **固定收支表（`recurring_rules` / `recurring_templates`）**：
   - *不建理由*：目前採手動記帳。固定或週期性排程（如每月房租、訂閱服務、固定薪資自動生成）日後可作為樣板排程表（Cron Job Template）加入，不影響現行底層資料表。
3. **載具與自動匯入表（`carrier_invoices` / `carrier_sync_logs`）**：
   - *不建理由*：避免在初版引入財政部電子發票整合服務平台的 API 介接、登入 Token 與輪詢同步複雜度。現行 `invoices` 與 `invoice_items` 表結構已完全相容電子發票欄位，未來可無縫掛接匯入模組。
4. **即時股價與報價歷史表（`stock_prices` / `market_quotes`）**：
   - *不建理由*：記帳本首要計算「持有股數」與「歷史投入之加權平均成本」；即時未實現損益與市價評價需介接外部即時報價 API，本階段不引入額外的外部連線與股價暫存資料表。
5. **銀行同步與開放銀行串接表（`bank_connections` / `sync_credentials`）**：
   - *不建理由*：本系統為純本機／自用後端，不進行自動化銀行網銀爬蟲或 Open Banking 認證連線，所有帳務異動由使用者自行確認後寫入。
6. **複式記帳會計科目與傳票表（`journal_entries` / `accounts_chart`）**：
   - *不建理由*：本設計採用個人友善且直覺之「帳戶實體流水制」，透過單筆流水帳配合移轉（Transfer）即可完整精確計算各帳戶餘額與損益，暫不需要引入龐大且學習門檻高的借貸平衡複式傳票體系。
7. **刪除日誌／軟刪除封存表（`audit_logs` / `deleted_records`）**：
   - *不建理由*：本階段明確禁止刪除帳務列，且外鍵全面採 `RESTRICT` 約束保護。如未來需要追蹤帳務誤植修正歷程，再評估引進審計稽核日誌。
8. **使用者帳號與家庭共享表（`users` / `user_profiles` / `family_groups`）**：
   - *不建理由*：本記帳本純粹個人獨佔自用，不發明多租戶、權限分級或家庭協同共享機制，維持極簡與高維護性。
